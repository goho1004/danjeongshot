## 회장 질문 답 (평문)

### 왜 1클릭=1HTTP인데 2콜 로그냐?

두 층이 다름.

1. **단정 서버 장부(bill-log)** — 「우리 앱이 Gemini에 HTTP를 몇 번 쐈나」  
   → 최근 초단위: **같은 초·같은 티켓 2발 없음**. 있어도 **주문(order)이 다르고 5~7초 차**.
2. **Google Studio Interactions** — 「Google 쪽에 찍힌 줄」  
   → 목록은 **분**만 보임. 디테일 초는 `6:08:50` / `6:08:51`처럼 **거의 동시**.  
   → 그건 「지금 master에서 컷 만들기 버튼 1번 = 2발」증거가 **아님**.  
   → 가능한 것: (a) **SHOT=3이던 옛 배포** 로그, (b) **첫컷+다시만들기**처럼 버튼 두 번, (c) **결제/주문을 두 번** 만든 테스트.

「정상」은 **지금 코드의 첫 컷 1클릭** 이야기. Studio에 쌓인 **옛/다른 행위 줄**과 섞어 보면 모순처럼 보임.

### 「다른 주문」이 어디서 나오냐?

숨은 주문이 아니라, **결제(checkout)할 때마다** 서버가 `ord_…` 새 ID를 만듦.

- 샌드박스로 다시 결제 · 탭 두 개 · 테스트 연타 → 주문 2개 → Gemini 각 1회 = Studio 2줄.  
- 장부에선 `preview:ord_aaa…` / `preview:ord_bbb…`처럼 **티켓·주문이 다름**.

### P0-1 · P0-2가 뭐냐? (기술 jargon → 평문)

- **P0-1:** 「다시 만들기」「A/S」는 **돈 나가는 호출을 먼저** 하고, **「이미 씀」표시는 나중**.  
  버튼이 거의 동시에 두 번 들어가면, 둘 다 「아직 안 썼네」통과 → **Gemini 2번 과금** → 나중에야 한쪽만 성공 처리.  
  첫 컷은 미리 자물쇠(`claim`)가 있는데, redo/asv는 그 자물쇠가 **호출 전**에 없음.

- **P0-2:** 자물쇠가 **Upstash(공유 Redis)**에 있음. Redis가 없거나 깨지면 **각 서버 자기 메모리**로 버팀.  
  Vercel은 서버가 여러 대라, A서버·B서버가 서로 모름 → **또 2번 쏠 수 있음**.  
  (문이 고장 나면 열어 두는 설계 = fail-open)
